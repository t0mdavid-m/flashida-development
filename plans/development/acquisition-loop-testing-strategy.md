## 1. Problem Statement

The existing testing strategy (Tiers 1-4) validates the **deconvolution bridge**: P/Invoke calls, struct marshaling, golden-file output from `Flash.exe <input> <output> <method.xml>` (positional args, no `-t` flag). This covers `FLASHIdaWrapper` and the C++ engine but leaves the C# acquisition loop untested.

The acquisition loop is the code path that runs on a real instrument. Its shape changes significantly across phases:

**Phases 0-4 (pre-simplification):**
```
Instrument event → Flash.ProcessSpectrum → DataPipe.Push
  → BufferBlock → TransformManyBlock (ProcessMS) → ActionBlock (OutputMS)
  → ScanScheduler.AddScan → scanControl.SetFusionCustomScan
```
Three processors (`IDAScanProcessor`, `FAIMSScanProcessor`, `QuantScanProcessor`) own all scan routing, tracking ID management, mode flags, and FAIMS CV cycling in C#.

**Phases 5-6 (post-simplification):**
```
Instrument event → Flash.ProcessSpectrum → DataPipe.Push
  → BufferBlock → ActionBlock (ProcessMS)
  → wrapper.ProcessScan → wrapper.GetNextScanCommand
  → scanFactory.BuildFromCommand → scanControl.SetFusionCustomScan
```
Single `UnifiedScanProcessor` delegates all logic to C++ via `ProcessScan`/`GetNextScanCommand`. `DataPipe` is two-stage. `ScanScheduler` is retained in Phase 5, deleted in Phase 6 (FAIMS CV cycling moves to C++).

**Phases 7-8 (final form):**
Same as Phases 5-6. C# architecture frozen; only C++ internals change (exploration engine, legacy cleanup).

### What is untested today

| Component | Responsible code (current) | Responsible code (final form) | Gap |
|-----------|---------------------------|-------------------------------|-----|
| Event loop | `Flash.cs:ProcessSpectrum` (static) | same | Scan arrival, queuing under burst, state transitions |
| Async pipeline | `DataPipe.cs` (3-stage) | `DataPipe.cs` (2-stage after Phase 5) | Backpressure, completion signals, task scheduling |
| Scan processing | `IDAScanProcessor` / `FAIMSScanProcessor` / `QuantScanProcessor` | `UnifiedScanProcessor` (Phase 5+) | Mode routing, tracking ID management, conditional MS2/MS3 logic |
| Scan scheduling | `ScanScheduler.cs` | C++ (Phase 6+) | Queue ordering, FAIMS CV cycling under load |
| Tracking ID lifecycle | C# `pendingMS2s` dictionary | C++ `FLASHIda` (Phase 4+) | Persistence across RT window, dictionary cleanup, scale |
| Error recovery | Processor `ProcessMS` catch blocks | `UnifiedScanProcessor`, `Flash.cs` | Empty spectra, bridge failures, malformed scan descriptions |

### Why continuity testing

The entire C# acquisition loop is rewritten in Phases 5-6. Continuity tests verify that the **behavioral output** — the sequence of scan commands produced for given inputs — remains identical before and after the rewrite. By capturing a reference in Phase 0 and asserting against it in every subsequent phase, these tests detect regressions regardless of which internal architecture is active. This is the same principle as the golden-file regression in testing-strategy.md, applied at the component level.

## 2. Design Principles

- **Assert behavioral output, not internal architecture.** Tests observe the scan commands the system produces for given inputs, using `ScanCommandRecord` (Section 4.4) to normalize across the legacy and unified architectures. The same assertions run from Phase 0 through Phase 8.
- **Mock the instrument, not the logic.** Thermo iAPI interfaces (`IMsScan`, `IFusionCustomScan`, `IFusionScans`) are replaced by lightweight test doubles. All decision logic runs as-is.
- **Test the pipeline end-to-end.** From `DataPipe.Push(mockScan)` through `IScanProcessor.ProcessMS` to captured scan commands — verifying the full async chain regardless of whether the `DataPipe` is 3-stage (legacy) or 2-stage (Phase 5+).
- **Inject timing, don't assume it.** Tests that verify deadline behavior use controlled delays and `TaskCompletionSource`, not `Thread.Sleep`.
- **Reuse existing spectrum data.** The same TSV files from `FlashIDA/test-data/spectra/` feed mock `IMsScan` objects, avoiding duplicate test data.
- **No new test tier.** These tests fit within the existing Tier 2 (DLL-dependent) and Tier 4 (stress) framework. They use NUnit in `Flash.Tests.csproj`. *(Phase 0 lesson: AL-CT tests are Tier 2, not Tier 1, because they load OpenMS.dll via P/Invoke. The spec says Tier 1 but the implementation correctly labels them Tier 2.)*

> **Phase 0 implementation note — assertion quality:** Several continuity tests as initially implemented have weak or tautological assertions. Known PROBLEMATIC tests (assertions are trivially true or assert on symptoms rather than behavior): CT13, CT14, CT17, CT22, CT27. Known WEAK tests (overly lenient pass conditions): CT01, CT08, CT09, CT10, CT18. These should be strengthened in a future phase when test infrastructure matures. Do not mistake passing of these tests for behavioral correctness.

## 3. Component Lifecycle

This table tracks how each acquisition loop component evolves across phases, determining which tests apply when.

| Component | Phases 0-2 | Phase 3 | Phase 4 | Phase 5 | Phase 6 | Phases 7-8 |
|-----------|-----------|---------|---------|---------|---------|------------|
| **DataPipe** | 3-stage (Buffer→Transform→Action) | unchanged | unchanged | **2-stage** (Buffer→Action) | unchanged | unchanged |
| **IScanProcessor** | `ProcessMS` + `OutputMS` | unchanged | unchanged | **`ProcessMS` only** (OutputMS removed) | unchanged | unchanged |
| **IDAScanProcessor** | Active; owns pendingMS2s, tracking IDs, mode flags | +shadow validation | +UseUnifiedBridge path | **Deleted** (merged into UnifiedScanProcessor) | — | — |
| **FAIMSScanProcessor** | Active; wraps IDAScanProcessor + FAIMS | +shadow validation | +UseUnifiedBridge path | Simplified (OutputMS removed) | **Deleted** | — |
| **QuantScanProcessor** | Active | +shadow validation | +UseUnifiedBridge path | **Deleted** | — | — |
| **UnifiedScanProcessor** | — | — | — | **Created** (calls ProcessScan/GetNextScanCommand) | unchanged | unchanged |
| **ScanScheduler** | Active; owns FAIMS CV cycling | unchanged | unchanged | Retained | **Deleted** (CV cycling moves to C++) | — |
| **ScanFactory** | Active | +`BuildFromCommand()` | Extended for all modes | unchanged | unchanged | unchanged |
| **Flash.cs** | Static event loop | unchanged | +UseUnifiedBridge branch | Flag removed; always uses UnifiedScanProcessor | ScanScheduler references removed | unchanged |
| **C++ tracking IDs** | — | Stub | **Full implementation** | unchanged | unchanged | unchanged |
| **C++ FAIMS state** | — | — | — | — | **Full implementation** | unchanged |

**Key transition:** Phase 5 is the inflection point. Before Phase 5, C# owns all scan logic. After Phase 5, C# is a thin relay between the instrument and C++ bridge. Continuity tests are built in Phase 0 to capture the behavioral baseline; they then verify that each subsequent phase preserves the same output.

## 4. Mock Architecture

Mock objects replace the Thermo instrument interfaces (`IMsScan`, `IFusionCustomScan`, `IFusionScans`) so that the full acquisition pipeline can run in a test environment without instrument hardware. The same mocks serve both the legacy (Phases 0-4) and post-simplification (Phase 5+) architectures.

### 4.1 MockMsScan

A minimal implementation of `IMsScan` for test use:

```csharp
// Flash.Tests/Mocks/MockMsScan.cs
internal class MockMsScan : IMsScan
{
    public double[] Mzs { get; set; }
    public double[] Intensities { get; set; }
    public string ScanDescription { get; set; }
    public int MsLevel { get; set; } = 1;
    public MockTrailer Trailer { get; }
    public bool IsDisposed { get; private set; }

    // Load from existing test data TSV
    // NOTE (Phase 0 lesson #9): Multi-scan TSV files require stopping at the
    // first scan boundary. FromTsv must break when it encounters a second "Spec"
    // header line, or it will mix peaks/RT from multiple scans and cause silent
    // zero-result failures from the deconvolution engine.
    public static MockMsScan FromTsv(string path, int scanIndex = 0) { ... }

    // Construct with known peaks for targeted tests
    public static MockMsScan WithPeaks(params (double mz, double intensity)[] peaks) { ... }

    public void Dispose() => IsDisposed = true;
}
```

`MockTrailer` implements the scan trailer dictionary interface, supporting `TryGetValue("FAIMS CV", ...)` for FAIMS tests and `TryGetValue("Access ID", ...)` for magic-scan detection.

### 4.2 MockScanFactory

Replaces `ScanFactory` for tests where `IFusionScans` is unavailable:

```csharp
// Flash.Tests/Mocks/MockScanFactory.cs
internal class MockScanFactory : ScanFactory
{
    public List<CapturedScan> CreatedScans { get; } = new();

    public override IFusionCustomScan CreateFusionCustomScan(
        ScanParameters parameters, int id = 0, double delay = 0,
        bool IsAGC = false, int AGCgroup = 1)
    {
        var scan = new MockCustomScan(parameters, id, delay, IsAGC);
        CreatedScans.Add(new CapturedScan(scan, DateTime.UtcNow));
        return scan;
    }

    // Added in Phase 3; override only needed from Phase 3 onward
    public override IFusionCustomScan BuildFromCommand(ScanCommand cmd)
    {
        var scan = MockCustomScan.FromScanCommand(cmd);
        CreatedScans.Add(new CapturedScan(scan, DateTime.UtcNow));
        return scan;
    }
}
```

**Phase 0-2:** Only `CreateFusionCustomScan` override is needed (`BuildFromCommand` does not exist yet).
**Phase 3+:** Both overrides are needed.

### 4.4 ScanCommandRecord — Phase-Independent Observation

The internal architecture changes at Phase 5 (3-stage → 2-stage DataPipe, three processors → one) and again at Phase 6 (ScanScheduler deleted). But the **behavioral output** — the sequence of scan commands the system produces for a given input — should remain constant.

`ScanCommandRecord` is a plain data class that captures the essential fields of a scan command regardless of whether it came from `IFusionCustomScan.Values` (legacy) or `ScanCommand` struct (Phase 6+):

```csharp
// Flash.Tests/ScanCommandRecord.cs
public class ScanCommandRecord
{
    public int MsnLevel { get; set; }           // 1=MS1, 2=MS2, 3=MS3
    public double PrecursorMz { get; set; }
    public double IsolationWidth { get; set; }
    public int CollisionEnergy { get; set; }
    public string Analyzer { get; set; }
    public string ScanDescription { get; set; }
    public bool IsAGC { get; set; }
    public double FaimsCV { get; set; }
    public string ActivationType { get; set; }

    // Phase 0-5: populate from IFusionCustomScan.Values dictionary
    public static ScanCommandRecord FromCustomScan(IFusionCustomScan scan)
    {
        var v = scan.Values;
        return new ScanCommandRecord
        {
            MsnLevel = v.TryGetValue("ScanType", out var st) && st == "MSn"
                ? (v.ContainsKey("SourceCIDEnergy") ? 3 : 2) : 1,
            PrecursorMz = v.TryGetValue("PrecursorMass", out var pm)
                ? double.Parse(pm) : 0,
            IsolationWidth = v.TryGetValue("IsolationWidth", out var iw)
                ? double.Parse(iw) : 0,
            CollisionEnergy = v.TryGetValue("CollisionEnergy", out var ce)
                ? int.Parse(ce) : 0,
            Analyzer = v.TryGetValue("Analyzer", out var an) ? an : "",
            ScanDescription = v.TryGetValue("ScanDescription", out var sd) ? sd : "",
            IsAGC = scan.IsPAGCScan,
            FaimsCV = v.TryGetValue("FAIMS CV", out var cv)
                ? double.Parse(cv) : 0,
            ActivationType = v.TryGetValue("ActivationType", out var at) ? at : "",
        };
    }

    // Phase 5+: populate from ScanCommand struct (returned by C++ bridge)
    public static ScanCommandRecord FromScanCommand(ScanCommand cmd)
    {
        return new ScanCommandRecord
        {
            MsnLevel = cmd.msn_level,
            PrecursorMz = cmd.num_isolation_stages > 0
                ? cmd.stages[0].precursor_mz : 0,
            IsolationWidth = cmd.num_isolation_stages > 0
                ? cmd.stages[0].isolation_width : 0,
            CollisionEnergy = cmd.num_isolation_stages > 0
                ? cmd.stages[0].collision_energy : 0,
            Analyzer = cmd.analyzer,
            ScanDescription = cmd.scan_description,
            IsAGC = cmd.is_agc != 0,
            FaimsCV = cmd.faims_cv,
            ActivationType = cmd.num_isolation_stages > 0
                ? cmd.stages[0].activation_type : "",
        };
    }
}
```

**How it is used:** Tests collect a `List<ScanCommandRecord>` from the system under test. In Phases 0-5, records come from `MockScanFactory.CreatedScans` via `FromCustomScan`. In Phase 5+, records come from either `FromCustomScan` (if still using ScanFactory) or `FromScanCommand` (if inspecting bridge output directly). The assertions are always the same: compare the list against a reference sequence.

### 4.5 Dependency Injection for Tests

Two small changes enable continuity tests to wire into the acquisition loop:

**Change 1 — Make `ScanFactory.CreateFusionCustomScan` virtual:**

```csharp
// ScanFactory.cs — add 'virtual' keyword
public virtual IFusionCustomScan CreateFusionCustomScan(
    ScanParameters parameters, int id = 0, double delay = 0,
    bool IsAGC = false, int AGCgroup = 1)
```

This allows `MockScanFactory` to override it. One keyword, zero behavioral change.

**Change 2 — Make `FLASHIdaWrapper` injectable in processor constructors:**

```csharp
// IDAScanProcessor.cs — add optional parameter
public IDAScanProcessor(MethodParameters parameters, ScanFactory factory,
                        ScanScheduler scheduler, double? staticCV = null,
                        FLASHIdaWrapper wrapper = null)
{
    flashIdaWrapper = wrapper ?? new FLASHIdaWrapper(parameters.IDA);
    // ... rest unchanged
}
```

Same pattern for `FAIMSScanProcessor` and `QuantScanProcessor`. Backward compatible — existing call sites pass nothing for the new parameter and get the old behavior.

**When to apply:** Both changes should be made in Phase 0 alongside the test project creation. They are non-behavioral and enable all subsequent acquisition loop tests.

`Flash.cs` is a static class that directly references Thermo types. Its event loop (`ProcessSpectrum`, `SendCustomScan`) is not directly testable without refactoring. The strategy tests the components that `Flash.cs` orchestrates rather than `Flash.cs` itself.

## 5. Continuity Tests (Phases 0-8, NEVER retired)

These tests use `ScanCommandRecord` (Section 4.4) to assert on the behavioral output of the acquisition loop regardless of internal architecture. They are introduced in Phase 0 and **never retired or replaced** — the same test code, the same assertions, and the same reference data run from Phase 0 through Phase 8. They are the thread that stitches the entire migration together.

#### Observation point

All continuity tests observe scan commands through `MockScanFactory.CreatedScans`. Both the legacy and unified paths go through `ScanFactory`:

- **Phases 0-4:** Processors call `scanFactory.CreateFusionCustomScan()` → `MockScanFactory` captures `MockCustomScan` → `ScanCommandRecord.FromCustomScan()`
- **Phase 5+:** `UnifiedScanProcessor` calls `scanFactory.BuildFromCommand()` → `MockScanFactory` captures `MockCustomScan` → `ScanCommandRecord.FromCustomScan()` (the mock populates `.Values` from the `ScanCommand` fields)

This works because `MockScanFactory` sits at the output boundary in both architectures. The `ScanCommandRecord` adapter normalizes the output.

#### Test harness helper

```csharp
// Flash.Tests/AcquisitionLoop/ContinuityTestHarness.cs
internal class ContinuityTestHarness : IDisposable
{
    public MockScanFactory ScanFactory { get; }
    public FLASHIdaWrapper Wrapper { get; }
    public DataPipe Pipeline { get; }

    // Constructs the correct pipeline for the current phase.
    // Phase 0-4: creates IDAScanProcessor (or FAIMS/Quant based on config)
    // Phase 5+: creates UnifiedScanProcessor
    // The test code does NOT need to know which one is active.
    public ContinuityTestHarness(string methodXmlPath) { ... }

    public void PushScan(MockMsScan scan) => Pipeline.Push(scan);

    public List<ScanCommandRecord> CollectResults()
    {
        // Complete pipeline, await drain, convert CreatedScans to records
        return ScanFactory.CreatedScans
            .Select(s => ScanCommandRecord.FromCustomScan(s.Scan))
            .ToList();
    }
}
```

When Phase 5 deletes the legacy processors, the harness constructor is updated to use `UnifiedScanProcessor`. The test assertions are unchanged.

#### How behavioral reference tests work across phases

Tests AL-CT06, CT15, CT16, CT19, CT21, CT24, CT25, CT26, CT28, CT30 each capture a mode-specific `ScanCommandRecord` sequence as a JSON golden file.

1. **Phase 0 (first run):** Each reference test collects records and serializes to `test-data/golden/continuity_*.json`. These files are committed. *(Phase 0 lesson #15: Golden-file capture requires 2 commits minimum — the first commit runs CI and produces the golden artifact; the second commit includes the captured golden file. Batch multiple golden captures into a single CI run where possible.)*
2. **Phases 1-4:** Tests load reference JSON, run same input, compare. Tolerance: 1e-4 relative for masses, exact for integers and strings.
3. **Phase 5:** Harness updated to `UnifiedScanProcessor`. Same reference files. If any mode produces different commands, the test fails.
4. **Phase 6:** ScanScheduler removed. FAIMS CV values flow through bridge. Same reference files.
5. **Phase 7:** Exploration reference (CT30) captured for the first time.
6. **Phase 8:** Same reference files, same assertions.

## 6. Phase Integration

### Phase 0: Mock infrastructure + continuity tests

Phase 0 creates the test project (`Flash.Tests.csproj`) and the two prerequisite changes (Section 4.5). This is the right time to also build mock infrastructure and continuity tests, because:

1. The test project is being created anyway.
2. The legacy code is in its pristine state — no shadow validation, no feature flags.
3. The behavioral reference (AL-CT06) must be captured before any code changes.

**Prerequisite changes applied:**
- `ScanFactory.CreateFusionCustomScan` → add `virtual` keyword
- `IDAScanProcessor`, `FAIMSScanProcessor`, `QuantScanProcessor` → add optional `FLASHIdaWrapper wrapper = null` parameter

**Tests introduced:**
- Mock infrastructure: `MockMsScan`, `MockScanFactory`, `MockCustomScan`, `MockTrailer`, `ScanCommandRecord`, `ContinuityTestHarness`

## 7. Test File Organization

```
FlashIDA/src/Flash.Tests/
  Mocks/
    MockMsScan.cs               # IMsScan test double
    MockCustomScan.cs           # IFusionCustomScan test double (with .Values dict)
    MockScanFactory.cs          # ScanFactory override (CreateFusionCustomScan; BuildFromCommand added Phase 3)
    MockTrailer.cs              # Scan trailer dictionary mock
    ScanCommandRecord.cs        # Phase-independent scan command abstraction (Section 4.4)
    ContinuityTestHarness.cs    # Configures pipeline for current phase; collects ScanCommandRecords
  AcquisitionLoop/
    ContinuityTests.cs          # AL-CT01 through AL-CT32 (NEVER deleted)
```

All tests are NUnit 3, running within `Flash.Tests.csproj`. They require `OpenMS.dll` (for `FLASHIdaWrapper` P/Invoke calls) but do NOT require Thermo iAPI DLLs — mock objects replace all Thermo interfaces.

> **Fixture organization (Phase 0 lesson #11):** Diagnostic or independent tests must go in their own `[TestFixture]` class, not in a fixture with `[OneTimeSetUp]` that may fail. A `[OneTimeSetUp]` failure marks ALL tests in the fixture as inconclusive (`site="Parent"`), including tests that don't depend on setup state.

> **NUnit working directory (Phase 0 lesson #12):** NUnit must be run from `FlashIDA/bin/` so that native DLLs (`OpenMS.dll` and dependencies) are found by the .NET runtime's DLL search path. Relative paths in tests (e.g., `..\\test-data\\`) depend on this specific working directory. CI runners and local test invocations must set `--work` accordingly.

> **Diagnostic output (Phase 0 lesson #10):** Use `Console.WriteLine()` for diagnostic output that must be visible in CI artifacts (NUnit XML `<output>` element). `TestContext.Error.WriteLine()` output does NOT appear in the XML results file.

> **NUnit runner flags (Phase 1 lessons #8, #9):** Pass `--agents=1 --timeout=300000` to the NUnit console runner. `--agents=1` prevents parallel worker processes from triggering simultaneous cold `calculateAveragine` cache initialization; `--timeout=300000` (5 min) allows that initialization to complete. If an NUnit agent crashes with an ambiguous error, add `--inprocess` temporarily to diagnose; remove it once the root cause is identified.

> **OPENMS_DATA_PATH (Phase 1 lesson #5):** Set `OPENMS_DATA_PATH` to `<workspace>/OpenMS/share/OpenMS` as an environment variable on every CI step that calls OpenMS P/Invoke functions. Without it the DLL cannot locate chemistry data files and crashes. This is required for all continuity tests — a DLL rebuild can silently change data path resolution. Do not rely on implicit resolution.

> **Continuity golden comparison (Phase 0 lesson #23):** The `ContinuityTestHarness.CollectResults()` behavioral reference tests (AL-CT06, CT15, CT16, CT19, CT21, CT24–CT26, CT28, CT30) use exact string equality on the serialized JSON, not tolerance-based field comparison. If a DLL rebuild changes floating-point output even within tolerance, the continuity golden files must be recaptured. This is intentional: exact comparison catches regressions that tolerance-based comparison would mask.

> **ContinuityTestHarness bypasses DataPipe (Phase 0 lesson #22):** The `ContinuityTestHarness` injects mock scans directly into the scan processor without going through the async `DataPipe` pipeline. This means AL-CT01–CT30 do not cover DataPipe backpressure, completion signal propagation, or task scheduling. DataPipe coverage is provided separately by P5-U04 (`DataPipe` unit test) and the fact that `Flash.exe` regression tests do use the full pipeline.

## 9. What Remains Untested

Even with this strategy, the following cannot be tested without instrument hardware:

| Area | Why untestable | Mitigation |
|------|---------------|------------|
| `Flash.ProcessSpectrum` event handler | Static method, references `IFusionMsScanContainer` events | Tested indirectly through DataPipe + processor tests |
| `Flash.SendCustomScan` | Calls `scanControl.SetFusionCustomScan` (Thermo API) | Output captured by `MockScanFactory` at processor level |
| Scan injection rejection | Thermo API may reject commands silently | Log-based monitoring on real instrument |
| Real-time deadline enforcement | MS2 injection window is vendor-specified | Can simulate with `Task.Delay` but not validated without hardware |
| Contact closure events | Hardware-only event from robot autosampler | Manual test during instrument commissioning |
| Acquisition state machine | `On`/`Standby`/`Off` requires `IAcquisition` from live instrument | Manual test during instrument commissioning |

These items should be addressed by a manual instrument commissioning checklist (out of scope for CI).
