# Parameter Optimization Plan — v6 (Minimal Bridge, Maximal C++)

**Date:** 2026-03-20
**Revision:** 6
**Design principle:** Two operational bridge functions: `ProcessScan` and `GetAndClearPendingCommands`. C++ makes ALL decisions — precursor selection, mode routing, MS3 targeting, exploration, quant follow-up, FAIMS CV cycling. C# is a stateless relay that extracts spectrum data, passes it to C++, converts returned ScanCommands into Thermo API objects, and submits them to the instrument.

---

## Issue 1 — Unified ProcessScan Bridge

### Desired behaviour
A single C++ entry point handles all scan levels (MS1 through MSn). C# passes only spectrum data and the scan description string. C++ resolves all precursor information, fragmentation parameters, and mode flags from its own internal tracking state. No per-mode bridge functions exist.

### Limitations of current design
The current bridge has ~20 specialized functions (`GetPeakGroupSize`, `GetIsolationWindows`, `DeconvolveMS2`, `GetBestMS2Masses`, `GetTopFragmentMatches`, `GetAmbiguityEnclosingIons`, `GetTerminalFragmentIons`, `HasMS2Deconvolution`, `GetMS2PeakGroupCount`, `ClearMS2Deconvolution`, `ProcessMS2ForTagBasedTargeting`, `IsDifferentiallyAbundant`, etc.). C# must orchestrate multi-step call sequences per scan type, maintaining mode-specific state (`pendingMS2s` dictionary, MS3 mode switches). Precursor info, fragmentation parameters (CE, isolation window, activation type), and mode flags are scattered between C# and C++ with no single source of truth.

### Proposed change

```cpp
extern "C" OPENMS_DLLAPI int ProcessScan(
    FLASHIda* obj,
    double* mzs, double* ints, int length,
    double rt_min,
    int ms_level,
    const char* scan_description);
```

**6 parameters.** Returns: number of commands pushed to the pending queue.

**How C++ resolves everything from scan_description:**

When C++ generates a ScanCommand (during MS1 processing), it assigns a tracking ID and stores full context in an internal map:

```cpp
// Internal to FLASHIda
struct PendingScanContext {
    double precursor_mz, mono_mass, isolation_width;
    int charge, collision_energy;
    std::string activation_type, fragmentation_method;
    int ms3_mode;              // -1 if not MS3
    std::string protein_sequence; // for MS3 modes 1-3
    // ... all parameters that were used to create this scan
};
std::unordered_map<int, PendingScanContext> pending_scan_map_;
```

When an MS2/MS3 result arrives via `ProcessScan`, C++ parses the 4-char tracking ID from the scan description, looks up `pending_scan_map_[id]`, and has full context — precursor mass, charge, isolation window, CE, activation type, mode flags. No parameters need to cross the bridge twice.

**Scan description format:**

```
TTTT <human-readable content>
```

- `TTTT` = exactly 4 base-36 characters (tracking ID), generated by C++ and assigned when pushing ScanCommands
- Space separator
- Human-readable content for users viewing raw files in Xcalibur/FreeStyle

Examples:
| Scan Type | Description | Length |
|-----------|-------------|--------|
| MS2 HCD | `0a1b 14038 19+ HCD` | 19 |
| MS2 ETD | `0a1c 14038 19+ ETD` | 19 |
| MS3 | `0a1d MS3 b12 3547 5+` | 21 |
| Exploration | `0a1e OPT 14038 19+ CE25` | 25 |
| Quant | `0a1f QNT 14038 19+` | 19 |
| MS1 | `0a20 MS1` | 8 |
| AGC | `0a21 AGC` | 8 |

**C++ parsing:** `int id = parseBase36(scan_description, 0, 4);`

**Tracking ID generation:** C++ maintains an atomic counter. `GetNextTrackingId` bridge function provides IDs to C# for MS1/AGC scans that are not command-channel-generated:

```cpp
extern "C" OPENMS_DLLAPI int GetNextTrackingId(FLASHIda* obj);
```

**Functions eliminated** (9 functions, replaced by ProcessScan + command channel):
- `GetPeakGroupSize`, `GetIsolationWindows`
- `DeconvolveMS2`, `GetBestMS2Masses`, `GetTopFragmentMatches`
- `GetAmbiguityEnclosingIons`, `GetTerminalFragmentIons`
- `HasMS2Deconvolution`, `GetMS2PeakGroupCount`, `ClearMS2Deconvolution`

**Functions absorbed into ProcessScan's internal routing:**
- `ProcessMS2ForTagBasedTargeting` (called internally when mode=tag/cond)
- `IsDifferentiallyAbundant` (called internally when mode=quant)

**Files:** `FLASHIdaBridgeFunctions.h/.cpp`, `FLASHIda.h/.cpp`, `FLASHIdaWrapper.cs`

## Issue 2 — Command Channel with Atomic Drain

### Desired behaviour
C++ pushes scan commands for ALL scan types (MS1, MS2, MS3, AGC, FAIMS) via a single command queue. C# drains atomically and converts to Thermo API objects. Commands describe full MSn scans with up to 10 isolation stages.

### Limitations of current design
C++ returns data via output arrays (GetIsolationWindows) or stored state (GetBestMS2Masses). C# must interpret results, build scan parameters, and create Thermo objects. Different result formats per function type.

### Proposed change

```cpp
const int MAX_ISOLATION_STAGES = 10;  // supports MSn up to MS10

struct IsolationStage {
    double precursor_mz;
    double isolation_width;
    int collision_energy;
    int charge;
    char activation_type[16];
    double first_mass;
    double last_mass;
    double reaction_time;       // ETD
    double reagent_max_it;      // ETD
    int reagent_agc_target;     // ETD
};

struct ScanCommand {
    int msn_level;                              // 1-10
    int num_isolation_stages;                   // msn_level - 1
    IsolationStage stages[MAX_ISOLATION_STAGES];

    double max_it;
    int agc_target;
    int orbitrap_resolution;
    char analyzer[32];
    double faims_cv;
    char scan_description[256];
    int priority;                               // 0=normal, 1=high
    uint64_t enqueue_timestamp_ms;              // set by C++ for timeout
    int is_agc;                                 // 1=AGC scan (Thermo-specific handling)
};
```

**C++ zero-initializes** all ScanCommands (`ScanCommand cmd = {};`).

**C# struct declarations:**

**C# conversion to ScanParameters:**

```csharp
ScanParameters BuildScanFromCommand(ScanCommand cmd) {
```


## Issue 3 — ScanScheduler: Simplified Queue with AGC/MS1 Bypass

### Desired behaviour
ScanScheduler is a simple FIFO with priority support. AGC and scheduled MS1 scans bypass the queue entirely — returned directly when due. FAIMS CV cycling is handled by C++ (pushes CV-specific commands via command channel). Stale scans are dropped based on `enqueue_timestamp_ms` from the ScanCommand. All configurable via method.xml.

### Limitations of current design
Single ConcurrentQueue with no priority, no timeout, no cycle time guarantee. FAIMS CV cycling logic (adaptive skip, CV state machine) embedded in ScanScheduler (~150 lines). AGC only fires when queue empties.

### Proposed change

**Replace ConcurrentQueue with LinkedList + lock.** Two lists: `priorityScans`, `standardScans`.

**FAIMS CV cycling fully in C++:** No `GetNextCV` bridge function needed. During ProcessScan (MS1), if FAIMS is configured, C++ pushes FAIMS-specific MS1+AGC commands with the correct `faims_cv` value via the command channel. C# just dequeues and submits. The pre-built `faimsDefaultScans[]` / `faimsAgcScans[]` arrays are eliminated — C# builds scans from ScanCommands dynamically.

**MS1/AGC tracking IDs from C++:** C# calls `GetNextTrackingId()` for any MS1/AGC scan it creates directly (empty-queue fallback). Stamps the ID in the scan description.

**No C# timestamp needed:** Timeout uses `enqueue_timestamp_ms` from the ScanCommand (set by C++ when it pushed the command). For C#-generated scans (fallback MS1/AGC), C# sets the timestamp field directly.

**`getNextScan()` flow:**

```
getNextScan()
│
▼
┌─[lock(sync)]──────────────────────────────────────────┐
│                                                        │
│  (1) AGC BYPASS                                        │
│  Is AGC due? ──YES──► return agcScan directly          │
│       │                                                │
│       NO                                               │
│       ▼                                                │
│  (2) MS1 CYCLE TIME                                    │
│  Elapsed > cycleTimeSeconds? ──YES──► return MS1 scan  │
│       │                              (stamp trackingId)│
│       NO                                               │
│       ▼                                                │
│  (3) TIMEOUT CLEANUP                                   │
│  Walk both lists:                                      │
│    if (now_ms - cmd.enqueue_timestamp_ms) > timeout:   │
│      remove, log "EXPIRED"                             │
│       │                                                │
│       ▼                                                │
│  (4) PRIORITY DEQUEUE                                  │
│  priorityScans non-empty? ──YES──► return first        │
│       │                                                │
│       NO                                               │
│       ▼                                                │
│  (5) STANDARD DEQUEUE                                  │
│  standardScans non-empty? ──YES──► return first        │
│       │                                                │
│       NO                                               │
│       ▼                                                │
│  (6) EMPTY FALLBACK                                    │
│  id = wrapper.GetNextTrackingId()                      │
│  stamp defaultScan with "TTTT MS1"                     │

│  return agcScan                                        │

```

Steps 1-2 guarantee AGC/MS1 are never starved regardless of queue depth.

## Issue 4 — Exploration Engine (Recognition Flow)

### Desired behaviour
C++ autonomously manages parameter exploration: creates exploration groups during MS1 processing, pushes variant scan commands, recognizes returning exploration results by tracking ID, scores them, and pushes the winning scan as a priority command. C# is not involved in any exploration logic.

### Limitations of current design
No exploration concept exists. MS2 results are processed independently with no comparative scoring across parameter variants.

### Proposed change

**Complete lifecycle:**

```
T0  MS1 arrives → ProcessScan(ms_level=1)
      C++ deconvolves → identifies precursor P (14038 Da, 19+)
      C++ creates ExplorationGroup #1 with 5 variants (CE 20,25,30,35,40)
      C++ pushes 5 ScanCommands with descriptions:
        "0a01 OPT 14038 19+ CE20"
        "0a02 OPT 14038 19+ CE25"  ... etc.
      C++ stores pending_scan_map_[0x0a01] = {mass=14038, charge=19, CE=20, group=1, variant=0}
        ... etc for each variant

T1  Variant CE20 result → ProcessScan(ms_level=2, desc="0a01 OPT 14038 19+ CE20")
      C++ parses tracking ID 0a01 → looks up pending_scan_map_ → group=1, variant=0
      C++ deconvolves MS2, scores fragmentation quality → 0.64
      C++ stores score in exploration_groups_[1].variants[0]
      received_count = 1/5 → not complete yet

T2-T4  Variants CE25, CE30, CE35 arrive similarly
      Scores: 0.87, 0.71, 0.65

T5  Variant CE40 result → ProcessScan(ms_level=2, desc="0a05 OPT 14038 19+ CE40")
      C++ scores → 0.62
      received_count = 5/5 → COMPLETE
      C++ finds winner: variant 1 (CE25, score 0.87)
      C++ pushes PRIORITY ScanCommand:
        "0a06 14038 19+ HCD" (winner scan, standard mode, priority=1)
      C++ cleans up exploration_groups_[1]

T6  Winner MS2 acquired → ProcessScan(ms_level=2, desc="0a06 14038 19+ HCD")
      C++ processes as standard MS2 (mode not OPT)
      PeakGroup metadata populated: optimization_group_id=1, is_best_variant=true, score=0.87
```

**Error handling:**
- Missing/corrupt description → fallback to standard MS2 mode
- Group not found → log warning, process as standard MS2
- Timeout (variant never arrives) → after configurable timeout, evaluate with partial results

**Files:** `FLASHIda.h/.cpp`

## Issue 5 — Fragmentation Quality Scoring

### Desired behaviour
C++ scores MS2 spectral quality for exploration variant ranking, with full access to raw spectrum, isolation windows, CE, and activation type.

### Limitations of current design
No MS2 quality metric exists. Additionally, the spectrum is currently NOT annotated with CE, isolation window, or activation type (confirmed: `DeconvolveMS2` only sets Precursor.MZ and Precursor.charge — CE, isolation, and activation are never stored on the Precursor object).

### Proposed change
**Fix:** Since C++ now has `pending_scan_map_` (Issue 1), when ProcessScan processes an MS2, it looks up the original scan parameters by tracking ID and sets them on the Precursor object before deconvolution:

```cpp
auto& ctx = pending_scan_map_[tracking_id];
Precursor precursor;
precursor.setMZ(ctx.precursor_mz);
precursor.setCharge(ctx.charge);
precursor.setIsolationWindowLowerOffset(ctx.isolation_width / 2.0);
precursor.setIsolationWindowUpperOffset(ctx.isolation_width / 2.0);
precursor.setActivationEnergy(ctx.collision_energy);
precursor.getActivationMethods().insert(parseActivation(ctx.activation_type));
spec.getPrecursors().push_back(precursor);
```

**Scoring function:**
```cpp
static double scoreFragmentationQuality(
    const DeconvolvedSpectrum& deconv_ms2,
    double precursor_mass, int precursor_charge);
```

All metadata now accessible via `deconv_ms2.getOriginalSpectrum().getPrecursors()[0]`.

Combines: weighted fragment count, intensity coverage, mass spread. Returns `double` in [0, 1].

**Files:** `FLASHIda.cpp` (annotation in processScan), `PeakGroupScoring.h/.cpp`

## Issue 6 — Unified C# Scan Processor

### Desired behaviour
One single `IScanProcessor` implementation handles ALL acquisition modes: standard DDA, inclusion, exclusion, deep, MS2 tagging, conditional MS2, MS3, isobaric quantification, FAIMS, and parameter optimization. C# ProcessMS is ~50 lines.

### Limitations of current design
Three separate processors (`IDAScanProcessor` ~770 lines, `FAIMSScanProcessor` ~180 lines, `QuantScanProcessor` ~230 lines) with duplicated spectrum extraction, different OutputMS behaviors, and mode-specific routing. Adding a new mode requires touching C# scheduling logic.

### Proposed change

**Single `UnifiedScanProcessor`:**

```csharp
public class UnifiedScanProcessor : IScanProcessor
{
    public IEnumerable<IFusionCustomScan> ProcessMS(IMsScan msScan)
    {
        var scans = new List<IFusionCustomScan>();
        if (msScan.Header["MassAnalyzer"] != "FTMS") return scans;

        // 1. Extract spectrum data once
        double[] mzs = msScan.Centroids.Select(c => c.Mz).ToArray();
        double[] ints = msScan.Centroids.Select(c => c.Intensity).ToArray();
        double rt = double.Parse(msScan.Header["StartTime"]);
        int msLevel = int.Parse(msScan.Header["MSOrder"]);
        msScan.Trailer.TryGetValue("Scan Description", out var scanDesc);

        // 2. Send to C++ (single call — C++ handles everything)
        int cmdCount = wrapper.ProcessScan(mzs, ints, mzs.Length, rt, msLevel, scanDesc ?? "");

        // 3. Drain all commands (MS2s, MS3s, follow-ups, exploration variants, FAIMS MS1s)
        if (cmdCount > 0)
        {
            var commands = wrapper.DrainPendingCommands(cmdCount);
            foreach (var cmd in commands)
                scans.Add(BuildScanFromCommand(cmd));
        }

        // 4. Null sentinel for default scheduling
        if (msLevel == 1) scans.Add(null);

        return scans;
    }

    public void OutputMS(IFusionCustomScan scan)
    {
        if (scan == null)
            scanScheduler.AddDefault();
        else if (scan.Values.ContainsKey("Priority") && scan.Values["Priority"] == "1")
            scanScheduler.AddPriorityScan(scan);
        else
            scanScheduler.AddScan(scan, 2);
    }
}
```

**Mode configuration passed to C++ at init:**

```csharp
// In constructor
wrapper.SetQuantificationConfig(enabled, reporterMzTol, foldChange, oneCondition, followupIdx);
wrapper.SetFAIMSConfig(cvValues, maxCVSkip, massThreshold);
// Standard DDA, inclusion, exclusion, deep, tagging, MS3 — all via existing FLASHIda(char* arg) constructor
```

**Flash.cs simplified:**
```csharp
flashIDAProcessor = new UnifiedScanProcessor(methodParams, scanFactory, scanScheduler, wrapper);
```

One processor. No branching. All modes controlled by C++ via configuration.

**Files eliminated:** `QuantScanProcessor.cs`, `FAIMSScanProcessor.cs`
**Files:** `IDAScanProcessor.cs` (rewritten as UnifiedScanProcessor), `Flash.cs`

## Issue 9 — Acquisition Metadata on PeakGroup

### Desired behaviour
PeakGroup carries detailed metadata about the optimization process that produced it, enabling downstream analysis, auditing, and machine learning.

### Limitations of current design
PeakGroup stores only deconvolution-derived properties (mass, charge, qScore, isotope fit). No fields for acquisition parameters, comparative scoring, timing, or cost tracking.

### Proposed change

**24+ fields in 5 categories:**

**A. Optimization Context:**
```cpp
int optimization_group_id_ = 0;       // 0 = not optimized
int variant_index_ = -1;
int total_variants_tested_ = 0;
bool is_best_variant_ = false;

```

**B. Acquisition Parameters Used:**
```cpp
double collision_energy_used_ = 0.0;
double isolation_width_used_ = 0.0;
std::string activation_type_used_;
double reaction_time_ms_ = 0.0;
double precursor_monoisotopic_mass_ = 0.0;
int precursor_charge_ = 0;
double precursor_mz_ = 0.0;
int precursor_scan_number_ = 0;
```

**C. Quality Scoring:**
```cpp
double fragmentation_quality_score_ = -1.0;  // [0,1]
double variant_score_rank_ = -1.0;           // this/best
float variant_tic_explained_ratio_ = 0.0f;
int variant_fragment_count_ = 0;

```

**D. Timing:**
```cpp

```

**E. Cost Tracking:**

**Gate:** `bool hasOptimizationMetadata() const { return optimization_group_id_ > 0; }`

**Serialization:** Optional CVParams in mzML. pyOpenMS exposure via `.pxd` bindings.

**Downstream queries enabled:**
- Compare CE effectiveness: group by `collision_energy_used_`, average `fragmentation_quality_score_`
- Audit exploration cost: sum `total_exploration_scans_` per mass range
- Train parameter prediction: features = (mass, charge, activation) → target = optimal CE

## Design Invariants

1. **Two operational bridge functions:** `ProcessScan` + `GetAndClearPendingCommands`. Everything else is init-time config.
2. **C++ resolves everything from tracking ID:** No precursor params, queue params, or mode flags cross the bridge at runtime.
3. **Atomic command drain:** Single mutex-protected call.
4. **AGC/MS1 bypass queue:** Returned directly when due.
5. **Old functions survive through Phase 5:** Phased migration.
6. **Spectra fully annotated:** CE, isolation, activation set from `pending_scan_map_` lookup.
7. **One C# processor:** `UnifiedScanProcessor` handles all modes.
